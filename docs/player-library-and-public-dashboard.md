# 玩家库与公网数据看板设计

## 目标与边界

本期把对局统计的主身份从会变化的直播名称提升为稳定的“玩家”，并允许管理员维护玩家展示名、创建玩家、绑定或改绑直播间。对局录像、OCR、B 站账号和管理能力仍只存在于本地 BLREC。

公网化只发布排行榜所需的只读数据，不把 NAS、SQLite 文件或当前管理 API 暴露到互联网。公开榜单源码位于仓库根目录的 `public-dashboard/`，它是一个拥有独立 `package.json`、构建产物和发布流程的 Angular 应用。原有 `webapp/` 只负责 BLREC 后台管理，随 NAS 镜像发布，不包含公开榜单路由。

本期不实现公网部署与同步程序；本文给出后续可直接实施的边界和协议。

## 领域模型

- 玩家：排行榜中的稳定身份，名称可编辑；一名玩家可以绑定多个直播间。
- 主播：录制时采集到的来源身份和名称，用于自动发现，不再作为统计主键。
- 直播间绑定：一个直播间当前只归属一名玩家。改绑会把该直播间已有和未来的对局统计一起移动到新玩家。
- 无直播间的历史录播：用录播与玩家的直接绑定兜底，避免丢失历史数据。

当前英雄胜率只统计已识别“录像主人公”且已识别英雄的对局。现有主人公识别只支持 3V3，因此 5V5 和大乱斗的总场次、胜负可以统计，但其玩家英雄统计要等主人公识别能力扩展后才会完整。

## 公网榜单产品规则

### 页面结构

公网榜单分为三个只读页面：

1. 总览：默认展示当前赛季，提供模式切换、本期王座、LIVE INDEX、玩家 Top 10 及英雄 Top 10。
2. 玩家综合榜：展示全部符合门槛的玩家，支持赛季、模式、关键词和分页切换。
3. 英雄胜率榜：展示全部符合门槛的英雄，支持赛季、模式、关键词和分页切换。

总览每次进入都回到当前赛季，不记忆上一次访问的历史赛季。历史赛季和跨赛季总榜只在两个详细榜单页切换，避免用户进入首页时误把旧榜当成正在更新的数据。

玩家总览默认展示榜首档案。用户点击 Top 3 或玩家 Top 10 中的其他玩家时，可以在当前页快速预览其档案；进入玩家综合榜后再查看完整排名。

### 榜单赛季

榜单赛季是本产品的统计周期，不代表《虚荣》仍有官方赛季。对局按 Asia/Shanghai 时区的直播开始时间归档：

| 赛季 | 时间范围 |
| --- | --- |
| 春季赛 | 当年 1 月 1 日 00:00（含）至 5 月 1 日 00:00（不含） |
| 夏季赛 | 当年 5 月 1 日 00:00（含）至 9 月 1 日 00:00（不含） |
| 秋季赛 | 当年 9 月 1 日 00:00（含）至次年 1 月 1 日 00:00（不含） |

当前北京时间落入的区间就是当前赛季。赛季键使用年份和英文季节，例如 2026-summer。迟到导入或重新识别的对局仍按原直播开始时间回填到对应赛季。

跨赛季总榜对全部有效对局重新聚合并重新计算胜率和名次，不累加赛季名次。这样某个玩家缺席一季或赛季样本量不同都不会造成错误权重。

### 模式归一

公开筛选固定为：

- 全部模式
- 3V3
- 乱斗
- 5V5

“乱斗”合并大乱斗与闪电战，因为当前历史数据难以稳定区分两者。内部数据继续保存原始模式和识别来源，公开快照只发布归一后的 brawl 聚合；将来识别可靠时可以重算并拆分，不需要修改历史对局。

“全部模式”是三个归一模式的去重合计，每场对局只能贡献给其中一个模式，不能重复计数。

### 玩家排名与本期王座

玩家在所选赛季和模式中至少有 20 场已确认对局才进入排名。第一版不生成综合积分，直接依次按胜率、胜场数、对局数和稳定玩家 ID 排序。20 场门槛负责抑制小样本高胜率；页面同时展示胜负和对局数，让排名依据可以直接核对。

“本期王座”直接取当前赛季、当前模式玩家综合榜的前三名：

- 第一名是榜首，使用金色视觉强调。
- 第二、三名是同一榜单的后续名次，不另算人气或直播热度。
- 切换模式时，王座、玩家 Top 10、榜首档案和 LIVE INDEX 同步切换。
- 符合门槛的玩家不足三名时展示全部；无人符合时展示说明门槛的空状态。

英雄在所选赛季和模式中至少有 20 场已确认主人公英雄对局才进入榜单，按胜率降序、对局数降序和英雄 ID 排序。页面展示原始胜率与样本量，不把未识别主人公或英雄的对局放进英雄分母。

### 总览和详细榜单

LIVE INDEX 不是排名分数，而是当前公开快照的状态区，固定展示收录玩家数、当前模式对局数、样本胜率、已识别英雄数、数据周期和最后更新时间。

总览的玩家榜与英雄榜分别最多展示 10 条；不足 10 条时展示全部。玩家档案默认对应榜首，展示当前模式对局、胜负、胜率，以及该赛季的模式构成和常用英雄。

玩家详细榜每页 10 条，检索范围包括玩家展示名、已绑定游戏别名、直播间号以及每个名称片段的完整拼音和拼音首字母；检索只过滤结果，不改变原始名次。英雄详细榜每页 10 条，分别索引官方中文名、英文名、全部社区别名、完整拼音和拼音首字母。每个名称是独立搜索片段，不把中文名、英文名和别名拼接后跨片段命中。英文不区分大小写，空格、连字符和全半角差异在匹配前归一化。

公开界面的英雄名称统一显示首选社区别名，英文名只作为内部稳定键和搜索词；一名英雄有多个社区别名时展示第一个，其他别名仍可检索。英雄榜不展示也不按“定位”检索。两个详细榜切换赛季、模式或关键词后都回到第一页。

## 本地数据设计

数据库迁移新增三张表：

- `vainglory_players`：稳定玩家身份、展示名、自动或手工来源、创建和更新时间。
- `vainglory_player_rooms`：直播间到玩家的一对一归属；玩家侧是一对多。
- `vainglory_player_sessions`：仅为没有有效直播间号的历史录播保存直接归属。

升级时，仅针对已有对局的录播回填玩家：优先按主播 UID 合并，其次按直播间号，再次按规范化主播名。此规则只负责生成可用的初始结果，管理员之后可以在玩家库中改名和改绑。

统计查询在读取时连接玩家绑定，而不是把玩家名称复制进对局。这样改名立即生效，直播间改绑也不需要批量重写历史对局。

## 本地管理能力

内部管理 API：

- `GET /api/v1/vainglory/players`
- `POST /api/v1/vainglory/players`
- `PATCH /api/v1/vainglory/players/{player_id}`
- `PUT /api/v1/vainglory/players/{player_id}/rooms/{room_id}`
- `DELETE /api/v1/vainglory/players/{player_id}/rooms/{room_id}`
- `GET /api/v1/vainglory/stats/players`
- `GET /api/v1/vainglory/stats/heroes?gameMode=3v3`

这些接口继续使用现有管理员认证，不作为公网 API。

数据页以玩家为单位展示总对局、胜负、胜率、模式分布、常用英雄和逐英雄胜率，并提供按模式筛选的全局英雄胜率榜。玩家库弹窗负责创建、改名、绑定和解绑直播间。

## 公网部署与同步决策

第一版使用“阿里云静态站点 + NAS 每日主动推送完整快照”。阿里云不访问 NAS，也不复制 SQLite；NAS 只建立出站 SSH 连接。榜单目前只有几十名玩家和几十名英雄，完整快照比增量同步简单、可恢复，而且不会产生玩家榜和英雄榜版本不一致的半成品状态。

```text
群晖上的 BLREC / SQLite（唯一事实源）
        │ 每日发布协调器：启动即检查，运行中每 10 分钟校验
        │ SSH 上传临时文件、校验摘要、原子替换清单
        ▼
阿里云 /srv/vg-dashboard/data
        │
        ├── manifest.json             当前版本指针
        └── snapshots/<snapshotId>.json  不可变快照
                    │
                    ▼
             Nginx + vg.luwei.host
```

静态前端由 `public-dashboard/` 独立执行 `npm ci && npm run build`，再把 `dist/` 作为版本目录发布到 `/srv/vg-dashboard/releases/<releaseId>`，验证后原子切换 `/srv/vg-dashboard/current` 软链接。BLREC 的 `webapp/` 构建和 NAS 镜像更新不会发布这个站点；反过来，站点发布也不会改动后台管理。

Nginx 已占用 80/443，第一版不需要额外开放应用端口，也不需要常驻云端 API 或 Docker 容器。

### 已核查的服务器条件

2026-08-03 通过本机 SSH 别名 `aliyun-server` 做过只读核查：

- 系统是 Ubuntu 24.04 LTS，Nginx 正常运行并监听 80/443，磁盘空间足够托管静态榜单。
- `vg.luwei.host` 已解析到该服务器，服务器已有 `*.luwei.host` 通配符证书，但尚无 `vg.luwei.host` 的 Nginx 站点配置。
- 服务器没有可用的 Docker 命令；该限制不影响静态站点方案。

正式部署时应创建权限受限的站点目录和专用发布账号，不让 NAS 持有日常使用的 root 凭据。首次建目录、安装公钥和启用 Nginx 配置属于一次性运维动作，部署前单独执行并验收。

建议的 Nginx 结构如下，证书路径沿用服务器现有通配符证书：

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name vg.luwei.host;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;
    server_name vg.luwei.host;

    ssl_certificate /etc/nginx/ssl/<wildcard-luwei-host>/fullchain.cer;
    ssl_certificate_key /etc/nginx/ssl/<wildcard-luwei-host>/private.key;

    root /srv/vg-dashboard/current;

    location = /data/manifest.json {
        root /srv/vg-dashboard;
        add_header Cache-Control "no-store" always;
    }

    location /data/snapshots/ {
        alias /srv/vg-dashboard/data/snapshots/;
        add_header Cache-Control "public, max-age=31536000, immutable" always;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

### 快照格式

快照使用普通 JSON，Nginx 在传输时压缩；字段采用显式白名单。加入赛季与每日发布状态后使用 schema version 2：

```json
{
  "schemaVersion": 2,
  "snapshotId": "20260803T020500Z-a1b2c3d4",
  "publicationDate": "2026-08-03",
  "generatedAt": "2026-08-03T02:05:00Z",
  "sourceLastMatchId": 12345,
  "currentSeasonKey": "2026-summer",
  "seasons": [
    {
      "key": "2026-summer",
      "startsAt": "2026-05-01T00:00:00+08:00",
      "endsAt": "2026-09-01T00:00:00+08:00"
    }
  ],
  "players": [],
  "rankings": {
    "2026-summer": {
      "players": {
        "all": [],
        "3v3": [],
        "brawl": [],
        "5v5": []
      },
      "heroes": {
        "all": [],
        "3v3": [],
        "brawl": [],
        "5v5": []
      }
    },
    "all-time": {
      "players": {},
      "heroes": {}
    }
  }
}
```

`snapshotId` 由源数据水位和内容 SHA-256 前缀组成，同一份内容重试时保持不变。`publicationDate` 是北京时间业务日期，是“今天是否已经发布”的幂等键；`generatedAt` 是实际生成时刻。站点显示最后更新时间，超过 36 小时没有新发布时提示“数据更新延迟”。

禁止发布的内容包括：B 站登录态和账号凭据、管理接口令牌、本地文件路径、录像和结算帧、内网地址、原始 OCR 调试数据、日志及未进入白名单的数据库列。

### 每日幂等发布协调器

不能只设置一个“每天零点触发”的内存计时器。容器可能在零点停机，或在发布失败后重启；正确模型是持续协调期望状态：

1. Worker 启动后立即读取远端 `manifest.json`，运行期间每 10 分钟重复检查。
2. 以 `Asia/Shanghai` 的今天作为期望 `publicationDate`。远端清单已经是今天且对应快照存在、摘要正确时直接跳过。
3. 未发布时，从同一个 SQLite 只读事务生成玩家、英雄和赛季完整快照，计算确定性 JSON 与 SHA-256；没有新增对局也照常发布当天版本。
4. 先通过 SSH 上传到临时文件，远端校验摘要后移动为 `snapshots/{snapshotId}.json`；最后用同目录临时文件原子替换 `manifest.json`。整个“复查清单并替换”步骤使用远端 `flock`，避免两个实例并发覆盖。
5. 只有远端清单切换成功才算当天发布成功。失败按 1、5、15、60 分钟退避重试，60 分钟封顶；容器重启后从第 1 步重新协调，不依赖丢失的内存状态。
6. 如果快照已上传但清单尚未切换，重试复用同一个 `snapshotId`；如果清单已切换但 SSH 响应丢失，下一次检查会识别当天已发布并跳过。因此每一步都可以安全重复。

远端 `manifest.json` 是跨容器重启的发布事实源；本地数据库可以另记尝试次数、最后错误和成功时间用于运维，但不能只靠本地“已执行”标记决定跳过。自动发布拒绝对局水位、玩家数或对局数倒退的快照，除非使用明确的人工回退流程。

## 运行与告警

- 发布协调器运行在 NAS/BLREC 容器内，只建立出站 SSH；NAS 不开放新入站端口，不公开 `2234`，公网也不调用管理员 API。
- 公网站点显示 `generatedAt`；超过 36 小时未发布时显示延迟状态并发送告警。
- 监控至少包含：目标发布日、远端实际发布日、最后成功时间、连续失败次数、快照摘要和字节数、玩家数、对局数、最后对局 ID。
- 保留最近 30 个不可变快照；清理任务不得删除当前清单引用的版本。错误发布通过原子回退清单恢复。

## 实施顺序

1. 在 BLREC 中增加只读快照导出器及契约测试，固定字段白名单、赛季聚合、别名和 schema version。
2. 增加每日发布协调器及测试，覆盖零点停机、失败后重启、响应丢失、重复执行、数据倒退和并发发布。
3. 将公网排行榜构建为独立只读静态产物，不包含管理入口和 NAS API 地址。
4. 在阿里云创建受限发布账号、站点目录和 `vg.luwei.host` Nginx 配置，先执行 `nginx -t` 再平滑加载。
5. 在测试路径运行一周，验证断网重试、重复推送、缓存、错误快照回退和过期告警后再正式开放域名。
