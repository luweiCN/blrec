# 玩家库与公网数据看板设计

## 目标与边界

本期把对局统计的主身份从会变化的直播名称提升为稳定的“玩家”，并允许管理员维护玩家展示名、创建玩家、绑定或改绑直播间。对局录像、OCR、B 站账号和管理能力仍只存在于本地 BLREC。

公网化只发布排行榜所需的只读数据，不把 NAS、SQLite 文件或当前管理 API 暴露到互联网。公开榜单源码位于仓库根目录的 `public-dashboard/`，它是一个拥有独立 `package.json`、构建产物和发布流程的 Angular 应用。原有 `webapp/` 只负责 BLREC 后台管理，随 NAS 镜像发布，不包含公开榜单路由。

当前已完成真实 SQLite 快照导出器、数据契约测试、独立静态看板的快照加载，以及阿里云 OSS/CDN、HTTPS 和证书自动续签同步；NAS 每日发布协调器待配置。

## 领域模型

- 玩家：排行榜中的稳定身份，名称可编辑；一名玩家可以绑定多个直播间。
- 主播：录制时采集到的来源身份和名称，用于自动发现，不再作为统计主键。
- 直播间绑定：一个直播间当前只归属一名玩家。改绑会把该直播间已有和未来的对局统计一起移动到新玩家。
- 无直播间的历史录播：用录播与玩家的直接绑定兜底，避免丢失历史数据。

当前公开数据以 3V3 为主，录像主人公和英雄识别也只在 3V3 中较为可靠。乱斗已经可以归档，但收录主播实际游玩的场次较少，因此样本很少；5V5 战绩匹配流程尚未完成，公开数据基本为空。模式页没有数据不代表服务器上没有玩家，只代表本站暂未收录到足够、可确认的直播样本。

## 公网榜单产品规则

### 页面结构

公网榜单分为八类只读页面：

1. 总览：默认展示当前赛季，提供本期王座、LIVE INDEX、玩家 Top 10 及英雄 Top 10。
2. 玩家综合榜：展示全部有有效对局的玩家，支持赛季、关键词和分页切换。
3. 英雄胜率榜：展示全部符合门槛的英雄，支持赛季、关键词和分页切换。
4. 玩家详情：展示玩家身份、当前排名与胜负、模式构成、近期状态、完整英雄池和跨赛季记录。
5. 英雄详情：展示英雄身份、当前排名与样本、各模式表现、常用该英雄的玩家和跨赛季记录。
6. 榜单说明：解释直播样本的数据边界、赛季与模式划分、玩家榜单分、英雄门槛和历史回填为何会改变排名。
7. 如何游玩：说明 Community Edition 当前状态、国内加速线路、东亚与东南亚匹配现状、5V5 内战和组队码用法；组队码低于 1600 时进入盲选，高于 1600 时进入征召 BP；低于 3000 时允许路人补位，高于 3000 时只用于已经凑齐六人或十人的内战。
8. 下载指南：独立说明美区 App Store 直接下载、国区历史已购找回、Android 4.13.4 XAPK、VGNA 社区客户端及第三方安装风险，不与排队教程混在同一页面。

比赛模式是全站状态，唯一切换入口位于顶部栏。首次访问默认选择 3V3；用户
选择其他模式后写入浏览器本地存储，刷新和跨页面访问都保持该模式。详情页与
榜单页同步响应顶部模式，页面内部不再重复放置模式控件。

总览每次进入都回到当前赛季，不记忆上一次访问的历史赛季。历史赛季和跨赛季总榜只在两个详细榜单页切换，避免用户进入首页时误把旧榜当成正在更新的数据。

玩家总览默认展示榜首档案。用户点击 Top 3 或玩家 Top 10 中的其他玩家时，可以在当前页快速预览其档案；进入玩家综合榜后再查看完整排名。

### 榜单赛季

榜单赛季是本产品的统计周期，不代表《虚荣》仍有官方赛季。对局按 Asia/Shanghai 时区的直播开始时间归档：

| 赛季 | 时间范围 |
| --- | --- |
| 春季赛 | 当年 1 月 1 日 00:00（含）至 5 月 1 日 00:00（不含） |
| 夏季赛 | 当年 5 月 1 日 00:00（含）至 9 月 1 日 00:00（不含） |
| 秋季赛 | 当年 9 月 1 日 00:00（含）至次年 1 月 1 日 00:00（不含） |

当前北京时间落入的区间就是当前赛季。赛季键使用年份和英文季节，例如 2026-summer。迟到导入或重新识别的对局仍按原直播开始时间回填到对应赛季。

跨赛季总榜对全部有效对局重新聚合并重新计算胜率和名次，不累加赛季名次。这样某个玩家缺席一季或赛季样本量不同都不会造成错误权重。

### 模式归一

公开筛选固定为：

- 全部模式
- 3V3
- 乱斗
- 5V5

“乱斗”合并大乱斗与闪电战，因为当前历史数据难以稳定区分两者。内部数据继续保存原始模式和识别来源，公开快照只发布归一后的 brawl 聚合；将来识别可靠时可以重算并拆分，不需要修改历史对局。

“全部模式”是三个归一模式的去重合计，每场对局只能贡献给其中一个模式，不能重复计数。

### 玩家排名与本期王座

玩家只要在所选赛季和模式中有已确认对局就进入排名。榜单分采用 Beta-Binomial 贝叶斯模型的 90% 可信下界并映射到 0—1000 分：以当前模式的全量样本胜率作为基线，先加入 20 场等效先验，再按直播开始时间加入玩家本赛季的实际胜负。这样同样胜率下，样本更多的玩家会获得更稳定的分数；少量连胜不会直接占据榜首。为避免整数取整吞掉单场反馈，当可信下界取整后没有变化时，胜场至少增加 1 分，负场至少减少 1 分；这项补偿不取代可信下界。低于 5 场仍参与排名，但标记为“定位中”。同分时依次按对局数、原始胜率和稳定玩家 ID 排序。

每个赛季都会继承上一赛季的后验能力，其中 25% 进入本赛季先验、其余 75% 回归模式基线；跨过一个没有参赛的赛季时继承权重衰减为 12.5%，更长时间未参赛则回到统一基线。快照每次都按时间从最早赛季重新计算到当前赛季，因此历史数据补录后，受影响赛季以及后续赛季的分数会在下一次发布时一起更新。跨赛季总榜则对全部有效对局独立计算，不叠加赛季名次或赛季分数。

“本期王座”直接取当前赛季、当前模式玩家综合榜的前三名：

- 第一名是榜首，使用金色视觉强调。
- 第二、三名是同一榜单的后续名次，不另算人气或直播热度。
- 切换模式时，王座、玩家 Top 10、榜首档案和 LIVE INDEX 同步切换。
- 有有效对局的玩家不足三名时展示全部；无人时展示空状态。

英雄在所选赛季和模式中至少有 20 场已确认主人公英雄对局才进入榜单，按胜率降序、对局数降序和英雄 ID 排序。页面展示原始胜率与样本量，不把未识别主人公或英雄的对局放进英雄分母。

### 总览和详细榜单

LIVE INDEX 不是排名分数，而是当前公开快照的状态区，固定展示收录玩家数、当前模式对局数、样本胜率、已识别英雄数、数据周期和最后更新时间。

总览的玩家榜与英雄榜分别最多展示 10 条；不足 10 条时展示全部。玩家档案默认对应榜首，展示当前模式对局、胜负、胜率，以及该赛季的模式构成和常用英雄。

玩家详细榜每页 10 条，检索范围包括玩家展示名、已绑定游戏别名、直播间号以及每个名称片段的完整拼音和拼音首字母；检索只过滤结果，不改变原始名次。英雄详细榜每页 10 条，分别索引官方中文名、英文名、全部社区别名、完整拼音和拼音首字母。每个名称是独立搜索片段，不把中文名、英文名和别名拼接后跨片段命中。英文不区分大小写，空格、连字符和全半角差异在匹配前归一化。

公开界面的英雄名称统一显示首选社区别名，英文名只作为内部稳定键和搜索词；一名英雄有多个社区别名时展示第一个，其他别名仍可检索。英雄榜不展示也不按“定位”检索。两个详细榜切换赛季、顶部模式或关键词后都回到第一页。玩家与英雄名称提供详情入口；详情页继续支持历史赛季与跨赛季总榜切换。

## 本地数据设计

数据库迁移新增三张表：

- `vainglory_players`：稳定玩家身份、展示名、自动或手工来源、创建和更新时间。
- `vainglory_player_rooms`：直播间到玩家的一对一归属；玩家侧是一对多。
- `vainglory_player_sessions`：仅为没有有效直播间号的历史录播保存直接归属。

升级时，仅针对已有对局的录播回填玩家：优先按主播 UID 合并，其次按直播间号，再次按规范化主播名。此规则只负责生成可用的初始结果，管理员之后可以在玩家库中改名和改绑。

统计查询在读取时连接玩家绑定，而不是把玩家名称复制进对局。这样改名立即生效，直播间改绑也不需要批量重写历史对局。

## 本地管理能力

内部管理 API：

- `GET /api/v1/vainglory/players`
- `POST /api/v1/vainglory/players`
- `PATCH /api/v1/vainglory/players/{player_id}`
- `PUT /api/v1/vainglory/players/{player_id}/rooms/{room_id}`
- `DELETE /api/v1/vainglory/players/{player_id}/rooms/{room_id}`
- `GET /api/v1/vainglory/stats/players`
- `GET /api/v1/vainglory/stats/heroes?gameMode=3v3`

这些接口继续使用现有管理员认证，不作为公网 API。

数据页以玩家为单位展示总对局、胜负、胜率、模式分布、常用英雄和逐英雄胜率，并提供按模式筛选的全局英雄胜率榜。玩家库弹窗负责创建、改名、绑定和解绑直播间。

## 公网部署与同步决策

第一版使用“阿里云 OSS 静态对象 + CDN + NAS 每日主动推送完整快照”。阿里云不访问 NAS，不复制 SQLite，也不运行常驻 API。NAS 只通过 HTTPS 调用 OSS 接口。榜单目前只有几十名玩家和几十名英雄，完整快照比增量同步简单、可恢复，而且不会产生玩家榜和英雄榜版本不一致的半成品状态。

```text
群晖上的 BLREC / SQLite（唯一事实源）
        │ 只读事务生成完整 JSON 快照
        │ 发布协调器：启动即检查，运行中定期校验
        │ HTTPS / OSS 最小权限上传
        ▼
阿里云 OSS Bucket
        │
        ├── index.html / 带哈希的站点资源
        └── data
             ├── manifest.json                    当前版本指针
             ├── avatars/<playerId>.jpg           绑定直播间头像
             └── snapshots/<snapshotId>.json      不可变快照
                    │
                    ▼
             阿里云 CDN + vg.luwei.host
```

静态前端由 `public-dashboard/` 独立执行 `npm ci && npm run build`，构建产物和数据快照发布到同一 Bucket。BLREC 的 `webapp/` 仍只是 NAS 后台管理页，不会被公网发布。日常数据更新只上传 `data/`；站点代码有新的已验证构建时，同一协调器再同步静态资源，不在 NAS 上自动 `git pull` 未经验证的代码。

这个方案不占用原阿里云服务器端口，也不在云服务器上运行榜单站点、Docker 或公网 API。`vg.luwei.host` 通过 CNAME 指向 CDN 加速域名；OSS 是回源站，不直接暴露 NAS。云服务器只复用现有 Nginx UI 的通配符证书，并由 systemd oneshot 定时任务将续签结果同步到 CDN。

推荐 Bucket 保持私有并启用 CDN 回源授权。站点与数据同域，不需要 CORS。CDN/OSS 规则固定为：

- `index.html` 和 `data/manifest.json`：不缓存，每次回源校验。
- `data/snapshots/*` 与带哈希的 JS/CSS/图片：一年缓存并标记 `immutable`。
- `data/avatars/*`：缓存一天；每日发布时按稳定玩家 ID 覆盖，页面失败时回退到代表英雄头像。
- SPA 未命中路径回退到 `/index.html`。
- HTTP 请求使用 301 跳转到相同路径的 HTTPS 地址。
- HTTPS 证书由现有 Nginx UI 签发和续期；云服务器每小时比较叶证书指纹，变化时才通过阿里云 CDN API 上传并启用，私钥不进入命令行、日志、NAS 日常发布账号或仓库。

证书同步以 CDN 当前返回的证书为幂等事实源，不维护本地“已同步”标记。服务启动前检查域名覆盖、剩余有效期和证书私钥匹配；上传后轮询确认 CDN 已启用同一指纹。systemd timer 使用 `Persistent=true`，错过计划时间、请求失败或服务器重启后都会补跑。新增的 CDN 授权仅覆盖 `vg.luwei.host` 的证书读取和更新操作，凭据保存在云服务器 root-only 配置中。

### 快照格式

快照使用普通 JSON，CDN 在传输时压缩；字段采用显式白名单。快照使用 schema version 2，当前指针另存为 schema version 1 的 `manifest.json`：

```json
{
  "schemaVersion": 2,
  "snapshotId": "20260803T020500Z-a1b2c3d4",
  "publicationDate": "2026-08-03",
  "generatedAt": "2026-08-03T02:05:00Z",
  "sourceLastMatchId": 12345,
  "sourceMatchCount": 701,
  "currentSeasonKey": "2026-summer",
  "seasons": [
    {
      "key": "2026-summer",
      "startsAt": "2026-05-01T00:00:00+08:00",
      "endsAt": "2026-09-01T00:00:00+08:00"
    }
  ],
  "standings": {
    "2026-summer": {
      "players": [],
      "heroes": []
    },
    "all-time": {
      "players": [],
      "heroes": []
    }
  }
}
```

`snapshotId` 由源数据水位和内容 SHA-256 前缀组成，同一份内容重试时保持不变。`publicationDate` 是北京时间业务日期，是“今天是否已经发布”的幂等键；`generatedAt` 是实际生成时刻。站点显示最后更新时间，超过 36 小时没有新发布时提示“数据更新延迟”。

禁止发布的内容包括：B 站登录态和账号凭据、管理接口令牌、本地文件路径、录像和结算帧、内网地址、原始 OCR 调试数据、日志及未进入白名单的数据库列。

### 每日幂等发布协调器

不能只设置一个“每天零点触发”的内存计时器。容器可能在零点停机，或在发布失败后重启；正确模型是持续协调期望状态：

1. Worker 启动后立即通过 OSS 内网或公网 Endpoint 直接读取 `data/manifest.json`（不经 CDN），运行期间每 10 分钟重复检查。
2. 以 `Asia/Shanghai` 的今天作为期望 `publicationDate`。远端清单已经是今天且对应快照存在、摘要正确时直接跳过。
3. 未发布时，从同一个 SQLite 只读事务生成玩家、英雄和赛季完整快照，计算确定性 JSON 与 SHA-256；没有新增对局也照常发布当天版本。
4. 先上传不可变的 `data/snapshots/{snapshotId}.json`，再通过 OSS 校验字节数与摘要，最后 PUT `data/manifest.json`。单个 OSS 对象替换是原子可见的，且清单始终最后发布；本地单例锁避免同一 NAS 上两个协调器并发。
5. 只有远端清单切换成功才算当天发布成功。失败按 1、5、15、60 分钟退避重试，60 分钟封顶；容器重启后从第 1 步重新协调，不依赖丢失的内存状态。
6. 如果快照已上传但清单尚未切换，重试复用同一个 `snapshotId`；如果清单已切换但 OSS 响应丢失，下一次检查会识别当天已发布并跳过。因此每一步都可以安全重复。

远端 `manifest.json` 是跨容器重启的发布事实源；本地数据库可以另记尝试次数、最后错误和成功时间用于运维，但不能只靠本地“已执行”标记决定跳过。自动发布拒绝对局水位、玩家数或对局数倒退的快照，除非使用明确的人工回退流程。

## 运行与告警

- 发布协调器运行在 NAS/BLREC 容器内，只发起 OSS HTTPS 出站请求；NAS 不开放新入站端口，不公开 `2234`，公网也不调用管理员 API。
- 证书同步运行在阿里云服务器的 systemd oneshot 服务中，不监听端口；每小时检查一次，证书未变化时只读后退出。
- 公网站点显示 `generatedAt`；超过 36 小时未发布时显示延迟状态并发送告警。
- 监控至少包含：目标发布日、远端实际发布日、最后成功时间、连续失败次数、快照摘要和字节数、玩家数、对局数、最后对局 ID。
- 保留最近 30 个不可变快照；清理任务不得删除当前清单引用的版本。错误发布通过原子回退清单恢复。

1. 已完成：在 BLREC 中增加只读快照导出器及契约测试，固定字段白名单、赛季聚合、别名和 schema version。

3. 待实施：增加 OSS 每日发布协调器及测试，覆盖零点停机、失败后重启、响应丢失、重复执行、数据倒退和并发发布。
