# 给 DeepSeek v4 Flash 的任务提示词

你现在接手的是 BLREC 项目中的《虚荣》（Vainglory）结算界面识别模型。请直接检查仓库并完成打标工具、数据集流水线、模型训练、评估和可部署模型，不要只给设计建议。

## 最终目标

训练一个小型视觉模型。对视频中的单帧图片，模型必须直接判断：

- `result_page`：这是完整、可用于提取战绩的游戏结算界面；
- `not_result_page`：其他一切画面。

当且仅当输出 `result_page` 时，同时返回结算面板的边界框和置信度。积分板、死亡后打开的战绩面板、复活倒计时画面、游戏 HUD、观战 HUD、回放画面、英雄选择、游戏大厅、加载/黑屏、其他 APP 和其他游戏都必须直接输出 `not_result_page`。

这是一个硬性边界：**禁止用 OCR 判断图片是不是结算界面；禁止先把“疑似画面”交给 OCR，再根据 OCR 是否读出比赛时长、胜负或玩家数据来淘汰。** OCR 只会在本模型已经确定输出 `result_page` 后用于提取结构化字段，不参与分类。

## 当前实现和真实基线

- 当前代码：`src/blrec/vainglory/result_detection.py`。
- 当前模型：`apps/analysis-worker/src/blrec_analysis_worker/models/result-panel.onnx`。
- 当前 Worker 会对整段视频按 4 FPS 解码，用 ONNX Runtime 的 CoreML Provider 逐帧调用模型，然后把相邻命中合并。
- 一段 87 分 46 秒的真实视频共扫描 21,065 帧，CoreML 扫描耗时约 449 秒。旧模型命中 147 帧，合并为 11 段；其中只有 2 段是真结算页，另外 7 段是游戏内积分板，2 段是其他游戏画面。已知的 2 个真结算页都被找到。
- 因此首要问题是积分板等 hard negative 的误报；优化精度时不能丢掉短暂、半透明、窗口化或低画质的真结算页。

## 必须覆盖的画面

正样本至少覆盖：

- 3V3、5V5、大乱斗及不同胜负方；
- 中文和英文客户端；
- 原生游戏、观战、回放中的真正结算页；
- PC 模拟器窗口化、画面四周黑边、非 16:9、缩放、录屏画中画；
- 低码率、模糊、色偏、掉帧、遮挡；
- 只出现约 0.6 秒、尚未完全淡入的半透明结算页；
- 结算面板只占原视频一部分的情况。

负样本必须重点覆盖：

- 3V3/5V5 游戏内积分板，包括玩家死亡、英雄头像带蒙版和复活倒计时；
- 玩家长时间打开积分板，随后直接切到结算页的前后连续帧；
- 顶部带比分/计时器的普通 HUD、观战 HUD 和回放 HUD；
- 击杀、投降、胜利动画、水晶爆炸、黑屏、加载、游戏大厅、英雄选择；
- 其他 APP、桌面、网页、直播间 UI 和其他游戏中相似的面板；
- 旧模型高置信度误报的全部画面。

## 打标工具

先实现一个本地可运行的打标工具，供人工持续补充数据。要求：

1. 可以导入一个或多个视频，按指定 FPS 抽帧，也能导入旧模型命中帧、命中前后邻近帧和随机背景帧。
2. 不得只展示旧模型的疑似帧；必须混入足量随机负样本，否则无法衡量真实误报率。
3. 每个样本至少支持：`result_page`、`not_result_page`、`skip/uncertain`。
4. 正样本必须能框选结算面板；负样本可以记录仅用于分析的原因标签，例如 `scoreboard`、`death_scoreboard`、`hud`、`lobby`、`other_game`、`black_loading`，但训练模型的最终输出仍是二分类。
5. 显示当前帧及前后若干帧的时间轴预览，便于人工区分积分板到结算页的转场；模型推理仍以单帧为输入。
6. 支持键盘快捷键、撤销、自动保存、断点继续、去重和导出。
7. 数据清单使用可版本化的 JSONL，至少保存：源视频稳定标识、时间戳、图片哈希、二分类标签、可选原因标签、边界框、打标时间和数据集版本。不要写入账号 Cookie 或其他凭据。
8. 相邻帧和感知哈希近重复帧要分组，避免同一个画面被大量重复计权。

## 数据切分与训练

1. 按“整场视频/主播”划分 train、validation、test，禁止把同一视频的相邻帧拆进不同集合造成数据泄漏。
2. 优先采用适合 Apple Silicon 实时推理的轻量检测/分类结构。模型本身必须完成真结算页与积分板的区分。
3. 对 hard negative 做主动挖掘：每轮用新模型重扫未参与训练的完整视频，把高置信度误报回流到打标工具，再训练下一轮。
4. 对短暂、透明、模糊和窗口化正样本做符合真实录屏的增强，但不能用会改变 UI 语义的生成方式制造虚假样本。
5. 置信度阈值必须在独立验证集上校准。报告帧级 precision/recall、按事件合并后的 precision/recall、每小时视频误报段数，以及各 hard-negative 子类的结果。
6. 验收不能依赖 OCR 成功率；计算模型指标时完全禁用 OCR。

## 部署和性能约束

- 导出 ONNX，并确保 ONNX Runtime `CoreMLExecutionProvider` 可运行；如输出张量与当前 `OnnxResultPanelDetector` 不同，只做最小适配并写清输出协议。
- 当模型输出 `not_result_page` 时，程序不得创建 OCR 任务；输出 `result_page` 时才进入现有 OCR/英雄识别阶段。
- 在 Apple Silicon MacBook Pro 上以 4 FPS 扫描。目标是模型扫描一小时视频不超过 10 分钟，包含后续 OCR 的完整分析不超过 20 分钟。
- 提供 CPU 与 CoreML 的真实视频基准，记录视频时长、总帧数、推理耗时、候选事件数、真阳性、误报和漏报。
- 不要引入云端推理或外部视觉 API；最终推理必须完全本地运行。

## 交付物

1. 可运行的本地打标工具及使用说明；
2. 抽帧、去重、切分、训练、评估、hard-negative 回流和导出脚本；
3. 数据集格式说明与版本清单；
4. 最终 ONNX 模型及最小运行时适配；
5. 一份真实视频评估报告，明确列出积分板等误报是否已经消除；
6. 一条从原始视频、人工打标、训练到替换生产模型的完整可复现命令链。
