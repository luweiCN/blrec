# 给 DeepSeek v4 Flash：实现“虚荣视觉标注工作台”

你现在接手 BLREC 仓库中的《虚荣》（Vainglory）视觉数据标注工具。请直接检查仓库、实现并实际跑通，不要只提供设计稿、伪代码或建议。

仓库路径是 `/Users/luwei/code/ai/blrec`。开始前完整阅读仓库根目录的 `AGENTS.md`，严格遵守其中的代码、网络、NAS、安全和凭据要求。

## 一、这次要交付什么

实现一个本地 Web 应用，产品名称暂定为：

> 虚荣视觉标注工作台（Vainglory Vision Lab）

它不是只服务某一个模型的一次性打标页面，而是所有《虚荣》视觉模型共用的数据工作台：

1. 从 NAS 选择录制视频；
2. 按不同策略抽取原始视频帧和短片段；
3. 对画面进行统一、分层、可复用的人工标注；
4. 根据不同“训练目标”筛选任务并导出相应数据集；
5. 保存不可变的数据集版本，供以后反复训练、评估和比较模型。

第一阶段必须完整跑通“结算界面检测模型”的标注与导出流程，但数据结构和界面必须允许后续继续训练游戏状态、模式、窗口定位和同局判断模型。

这次只实现标注工作台、数据集导入导出和数据版本管理。**不要开始正式模型训练，不要替换生产模型，不要部署到 NAS 的生产容器。** 等用户完成第一轮人工标注并检查数据后，才进入训练阶段。

## 二、先检查并纠正现有原型

工作区可能已经存在尚未提交的原型：

`scripts/vainglory_labeling/`

先检查并复用其中确实正确的 NAS 读取、FastAPI、SQLite 和前端代码，不要为了重写而重写。但当前原型的以下设计不能作为最终方案：

1. 不能只按 3～5 秒均匀抽一帧；真实结算页可能只出现约 0.6 秒。
2. 不能只保存缩到 960 宽或 224×224 的图片；必须保留原始分辨率帧。
3. 不能把“大乱斗”写成 `Blitz`：
   - 大乱斗是 `aram`；
   - 闪电战是 `blitz`；
   - 二者必须是完全独立的模式。
4. 不能以随机图片 8:2 的方式划分训练集和验证集；同一视频和相邻帧不能跨集合。
5. 不能只训练 224×224 七分类模型；第一目标是能直接输出结算面板边界框的单类别检测数据集。
6. 当前 `frame_kind + is_result` 两个字段可能相互矛盾，必须改成一个权威的分层标签体系。
7. 当前缺少事件分组、原始图片哈希、感知哈希、边界框、标注版本和数据集版本。
8. `.venv/`、抽出的图片、SQLite 工作库、模型权重和账号凭据都不能提交到 Git。

## 三、核心产品原则

### 1. 一份共享数据，多种训练目标

首页先让用户选择“训练目标/标注任务”，而不是为每个模型复制一份图片：

- 结算界面检测；
- 游戏画面与游戏状态识别；
- 游戏模式识别；
- 游戏窗口/有效画面区域检测；
- 两张 HUD 是否属于同一局；
- 后续可新增任务。

底层视频、原始帧、事件和基础标注全部共享。训练目标只决定：

- 当前优先展示哪些样本；
- 哪些标注字段是本任务必填；
- 导出时生成什么格式和标签。

第一阶段不要创建没有功能的假按钮。结算检测、游戏状态、模式和窗口定位应能基于同一帧完成标注；“同局判断”可以使用双图标注视图，至少支持选择两张已有帧并标记 `same_match / different_match / uncertain`。

### 2. 原始数据永远保留

从视频抽出的帧必须保存原始分辨率和真实时间戳。不同尺寸只能是可重建的派生物：

- 原始帧：模型数据源，永久保留；
- 缩略图：只用于网页快速浏览；
- 训练图：导出数据集时根据目标生成，例如 640×640 letterbox；
- 不得用缩略图覆盖原图；
- 不得因为当前模型使用 640，就丢弃以后训练 960 模型需要的细节。

### 3. 以“事件/片段”为核心，不把相邻帧当成独立数据

“独立结算事件”指一局比赛结束后，连续出现的那一次结算界面。

例如结算页持续 12 秒，4 FPS 会得到 48 帧，但它们都属于同一个事件。工具应自动把相邻命中和感知哈希近似帧聚成一组，在一个约 6～10 秒的片段中展示。用户确认一次事件后，从中选择约 3～6 张有差异的代表帧：

- 刚淡入、半透明；
- 完整清晰；
- 有弹幕或其他遮挡；
- 主播点击按钮后的变化；
- 即将消失。

边界框可在同一事件内自动传播，用户只修正有变化的帧。不得把同一画面的几十张近重复帧全部等权放入训练集。

## 四、统一标注体系

字段必须是层级式、条件式的。界面只展示当前有意义的字段，不要求用户为每张图填写一长串无关选项。

### 1. 顶层：是否为《虚荣》画面

`content_family`：

- `vainglory`
- `not_vainglory`
- `uncertain`

如果不是《虚荣》，继续选择可选原因：

`non_vainglory_type`：

- `other_game`
- `desktop_or_app`
- `web_or_video_page`
- `stream_cover_or_overlay`
- `black_or_loading`
- `other`

如果选择 `not_vainglory`，不要再强迫用户填写游戏模式等字段。

### 2. 《虚荣》画面：游戏内还是游戏外

`game_context`：

- `in_match`
- `out_of_match`
- `transition`
- `unknown`

#### 游戏外画面 `out_of_match`

`screen_type` 可选：

- `main_lobby`：游戏大厅；
- `hero_roster`：英雄列表/英雄详情；
- `global_store`：游戏外商店；
- `matchmaking`：排队/匹配；
- `hero_select`：选英雄/阵容确认；
- `loading`：进入游戏前的加载；
- `settings`：游戏外设置；
- `other_out_of_match`。

#### 游戏内画面 `in_match`

`screen_type` 可选：

- `gameplay`：普通战斗画面；
- `scoreboard`：游戏内积分板；
- `death_scoreboard`：玩家死亡、头像有蒙版或复活倒计时的积分板；
- `ingame_shop`：游戏内装备商店；
- `skill_info`：技能介绍/技能详情；
- `settings_or_pause`：游戏内设置或暂停；
- `victory_defeat_animation`：水晶爆炸、胜利/失败动画，但尚未出现结算面板；
- `result_page`：真正的赛后结算界面；
- `spectate_or_replay_hud`：观战或回放 HUD；
- `other_in_match`。

“积分板”和“真正的结算界面”是本项目最重要的边界，标签说明必须在界面中随时可查看：

- 比赛仍在进行、临时打开的玩家数据面板始终是 `scoreboard` 或 `death_scoreboard`；
- 比赛结束后出现、包含最终胜负和整局数据的面板才是 `result_page`；
- 不能用画面右上角是否有 `REPLAY` 字样判断，因为某些客户端才有该标志；
- 不能用 OCR 结果反推是不是结算页。

### 3. 游戏模式

仅在画面提供足够证据时填写 `game_mode`：

- `3v3`
- `5v5`
- `aram`：大乱斗，随机英雄；
- `blitz`：闪电战，可以选英雄；
- `unknown`

模式不确定时必须允许 `unknown`，禁止为了完成标注而猜测。

### 4. 真人、人机、练习

这是独立于地图模式的 `match_kind`：

- `pvp`
- `bot`
- `practice`
- `unknown`

默认值必须是 `unknown`。只有画面上存在明确证据时才允许标记：

- 3V3 人机队友常见名称为 `Alpha Bot`、`Beta Bot` 等；
- 5V5 人机名称通常是“英雄称号 + 空格 + 英雄名”；
- 练习模式在 HUD 或结算界面通常只有玩家自己的一个英雄；
- 不能因为对局时间短、玩家挂机或很快投降就判断为人机/练习；
- 如果当前帧看不到玩家名称或英雄数量，就保持 `unknown`。

### 5. 视角

`view_context`：

- `played`：主播本人正在操作；
- `spectated`：观战；
- `replay`：回放；
- `unknown`。

### 6. 画面位置和边界框

支持在原图上绘制并编辑：

- `viewport_bbox`：完整游戏画面在直播视频中的范围；
- `result_panel_bbox`：真正结算面板的范围，仅 `result_page` 必填。

坐标必须相对原始图片保存，导出时再换算到训练图。需要支持：

- 全屏；
- 上下/左右黑边；
- PC 模拟器窗口；
- 游戏画面被缩小到直播画面一部分；
- 画中画；
- 裁剪不完整。

### 7. 画质和黑边如何标

这些信息值得保留，因为需要单独评估模型在低画质、窗口化和黑边情况下是否漏识别；但不能显著增加每帧操作时间。

`quality_flags` 使用可多选的异常标签：

- `blurred`
- `low_bitrate`
- `occluded`
- `translucent`
- `color_shift`
- `torn_or_corrupted`

正常画面默认不选任何异常，不需要用户每次点击“清晰”。

`black_bars` 和窗口状态优先由程序根据像素和 `viewport_bbox` 自动建议：

- `none`
- `top`
- `bottom`
- `left`
- `right`
- `multiple`

用户只在自动判断错误时修正。不要把画质和黑边设置为阻塞“保存并下一张”的必填项。

对于 `result_page`，额外允许一个辅助字段 `ocr_usable`：

- `yes`
- `no`
- `unknown`

它只用于后续挑选最清晰帧和分析 OCR 效果，不参与“是不是结算界面”的视觉分类。

## 五、数据来源和抽帧策略

### 1. NAS 视频导入

工具要能同步 NAS 上已有录制视频并展示：

- 主播；
- 房间号；
- 直播/录制时间；
- 文件名；
- 视频时长；
- 文件大小；
- BVID、分 P 和现有对局数量（如果数据库中存在）；
- 是否已经抽帧、已标多少帧。

支持按主播、时间、BVID、视频长度和标注状态搜索过滤，多选视频创建抽帧任务。

NAS 只作为只读视频来源，绝不能修改或删除录制文件。SSH 用户名和密码只能从 `SYNO_ADMIN_USERNAME`、`SYNO_ADMIN_PASSWORD` 读取，不能输出、写入 SQLite、日志、前端或仓库。

优先复用现有 BLREC API、数据库和媒体读取能力；如果确实需要 SSH，严格遵守 `AGENTS.md` 的 Expect、Docker 路径和凭据规则。

### 2. 一个训练目标可以选择多种抽帧配方

至少支持：

1. `existing_model_hits`：现有模型所有命中及其前后邻近帧；
2. `dense_around_candidate`：候选前后约 3～5 秒按 4 FPS 或 8 FPS 密集抽帧；
3. `uniform_random`：跨完整视频随机或分层抽取背景负样本；
4. `manual_timestamps`：导入浏览器插件或人工输入的时间点；
5. `dense_interval`：用户指定起止时间，对该短区间密集抽帧；
6. `transition_windows`：HUD 消失/出现、画面大幅变化附近的帧。

不得只展示旧模型认为“疑似结算”的图片。必须混入随机负样本，否则模型和评估都会产生严重偏差。

### 3. 时间戳必须真实

不能用“第几张 × 采样间隔”伪造时间戳。必须读取视频真实 PTS，并把毫秒时间戳与图片严格对应。分批视频还要保存所在 part、part 内时间和整场直播时间偏移。

### 4. 去重和事件分组

每张图片保存：

- SHA-256；
- 感知哈希；
- 相邻事件 ID；
- 来源抽帧策略；
- 生成该样本的模型版本及置信度（如有）。

完全相同图片不重复存储。感知相似且时间接近的帧自动分组，但用户可以拆分或合并事件。

## 六、标注界面和视觉设计

### 整体风格

采用专业视频剪辑/机器学习数据工作台风格，而不是普通后台管理页面：

- 深色主题，长时间看图不刺眼；
- 信息密度高，但层级清楚；
- 不使用大面积渐变、玻璃拟态、荧光色、夸张圆角或营销网站式大卡片；
- 不使用 emoji 充当功能图标；
- 图标使用简洁一致的线性图标；
- 字体使用 macOS 系统字体：`-apple-system, BlinkMacSystemFont, "PingFang SC", sans-serif`；
- 主要背景建议 `#0b0f14`，面板 `#121821`，边框 `#263241`；
- 主操作色使用克制的蓝色，例如 `#4f8cff`；
- 结算正样本使用绿色，负样本使用红色或暖灰，不确定使用黄色；
- 保证文字和控件对比度，焦点状态清晰，键盘可操作。

### 页面骨架

桌面端优先，建议最小宽度 1280px：

1. 左侧约 240px：
   - 训练目标；
   - 数据源；
   - 标注队列；
   - 数据检查；
   - 数据集版本；
   - 训练记录（先展示空状态，不启动训练）。
2. 顶部紧凑工具栏：
   - 当前任务；
   - 视频/主播；
   - part 和时间戳；
   - 已完成/总数；
   - 自动保存状态；
   - 撤销/重做。
3. 中央主画布：
   - 尽可能大地展示原始帧；
   - 支持适应窗口、100% 原始比例和缩放；
   - 支持绘制、移动、缩放 `viewport_bbox` 与 `result_panel_bbox`；
   - 不同边界框颜色和标签必须清晰。
4. 右侧约 320px 检查器：
   - 使用条件式分层标签；
   - 只显示当前有意义的字段；
   - 常用操作一键完成；
   - 展示清晰的标签定义，尤其是积分板与结算页区别。
5. 底部时间轴/胶片带：
   - 展示当前帧前后约 3～5 秒；
   - 4 FPS 或 8 FPS 缩略图；
   - 支持播放、暂停、逐帧、跳到事件首尾；
   - 标出旧模型命中、人工正负标签和当前代表帧。

左右面板和底部时间轴允许拖动调整尺寸。图片、缩略图和相邻样本要预取，切换时不能每张都长时间白屏。

### 键盘优先

至少支持并在界面显示快捷键：

- `R`：标记真正结算页；
- `N`：标记非结算页；
- `U`：不确定/跳过；
- `V`：虚荣画面；
- `G`：普通游戏中画面；
- `S`：积分板；
- `Space`：播放/暂停片段；
- `← / →`：逐帧；
- `Shift + ← / →`：上一个/下一个事件；
- `Enter`：保存并进入下一项；
- `Cmd/Ctrl + Z`：撤销；
- `F`：适应画布；
- 数字键或可配置按键用于常用子类。

输入备注或搜索框聚焦时不能误触全局快捷键。

### 标注效率

- 所有标注自动保存；
- 页面关闭后可断点继续；
- 保存后立即预取下一项；
- 可以把模式、视角、viewport 和质量属性批量传播到同一事件或用户选择的一组帧；
- 传播前显示影响范围，支持撤销；
- 模型预测默认不要在用户作答前高亮答案，避免人工被旧模型带偏；标完后可以显示预测与人工标签是否一致。

## 七、建议数据结构

SQLite 作为交互式工作库，JSONL 作为可版本化的权威导出。至少需要以下概念：

- `videos`：视频及 NAS 来源；
- `frames`：原始帧、真实 PTS、尺寸、哈希；
- `events`：连续片段/独立结算事件；
- `annotations`：统一分层标签；
- `boxes`：viewport 和 result panel；
- `pair_annotations`：同局/不同局双图标签；
- `model_predictions`：不同模型版本的预打分；
- `annotation_tasks`：训练目标及当前队列；
- `dataset_versions`：不可变数据集快照及切分；
- `audit_log`：撤销和修改记录。

JSONL 每条样本至少包含：

- 稳定 sample ID；
- 视频、session、part、BVID、主播等来源标识；
- 原始视频真实时间戳；
- 原始尺寸；
- SHA-256 和感知哈希；
- event ID；
- 完整分层标签；
- 原图坐标系的边界框；
- 画质和黑边辅助属性；
- 抽帧来源；
- 标注时间、标注版本；
- 数据集 split group；
- 不包含账号 Cookie、密码、token 或可复用登录凭据。

不要把同一事实存成两个可能冲突的布尔字段。例如 `screen_type=result_page` 就是结算页的权威结论，不再额外存一个可独立修改的 `is_result=true/false`；导出时可以派生布尔值。

## 八、数据集导出和版本

### 结算界面检测数据集

- 单类别：`result_panel`；
- 正样本必须有 `result_panel_bbox`；
- 负样本为空标注；
- 保留随机背景负样本和积分板 hard negative；
- 支持导出 YOLO detection 和 COCO detection；
- 同时导出权威 JSONL 清单。

### 其他任务

- 游戏状态：导出基于分层 `screen_type` 的分类数据；
- 游戏模式：只导出有可靠 `game_mode` 标签的样本；
- viewport：导出 `viewport_bbox` 检测数据；
- 同局判断：导出双图路径及 `same/different/uncertain`，也可以根据可靠的 match event ID 自动产生候选配对，人工抽查。

每次导出创建不可变版本，例如：

- `result-detector-v1`
- `game-state-v1`
- `game-mode-v1`

记录筛选条件、数量、标签分布、源视频、主播分布、创建时间和 Git commit。禁止覆盖已有版本。

训练/验证/测试划分必须以整场直播、视频 part 的同源关系、主播和事件组为单位，禁止随机按图片划分。同一视频、同一事件的相邻帧只能属于一个集合。

## 九、第一阶段的数量统计和数据检查

工作台要实时展示的不只是总帧数，还包括：

- 独立结算事件数；
- 结算正样本数；
- 积分板 hard negative 数；
- 随机负样本数；
- 主播数量；
- 3V3、5V5、大乱斗、闪电战分布；
- 中文/英文、窗口化、黑边、模糊、半透明等覆盖情况；
- 重复/近重复组；
- 冲突和缺失标注。

第一轮只需要支持用户逐步达到：

- 30～50 个独立结算事件；
- 每个事件约 3～5 个代表正样本；
- 合计约 120～250 张结算正样本；
- 约 800～1,500 张负样本，其中重点包含积分板；
- 训练第一版后再通过主动学习追加数据，而不是一开始人工标一万张。

## 十、安全和边界

- 不得输出、记录或提交 NAS 密码、Cookie、API key、Worker token；
- NAS 视频只读，不得移动、删除或覆盖；
- 不得修改生产 Compose、生产数据库或线上分析结果；
- 不得为了工具方便绕过仓库 `NetworkRouteManager` 约束新增生产网络连接；
- 大型图片、视频、SQLite、虚拟环境、依赖目录和训练权重必须 gitignore；
- 源码和小型 schema/示例清单可以提交；
- 保持改动只在标注工具及其文档范围，不重构 BLREC 录制、上传、发布或统计逻辑。

## 十一、完成标准

以下项目全部实际验证后才算完成：

1. 提供一条明确命令可启动本地 Web 应用；
2. 成功同步 NAS 视频清单，但不修改 NAS 文件；
3. 从一个真实视频按真实 PTS 抽取原始帧；
4. 能创建候选事件并显示前后时间轴；
5. 能完成 `是否虚荣 → 游戏内外 → 具体界面 → 模式/视角` 的条件式标注；
6. 能画 viewport 和结算面板边界框；
7. 能自动保存、刷新恢复、撤销、批量传播；
8. 能检测完全重复和相邻近重复样本；
9. 能生成一个包含正负样本的 `result-detector-v1` JSONL、YOLO 和 COCO 导出；
10. 导出切分不存在同视频/同事件跨集合泄漏；
11. UI 在 1440px 和更宽桌面窗口中布局清晰，提供最终截图；
12. README 写清安装、启动、NAS 导入、打标规则、快捷键、数据位置、备份和导出流程；
13. 提供一份简短的真实数据冒烟结果：用了哪个视频、抽了多少帧、建立多少事件、人工标注如何保存和导出；
14. 没有凭据、原始视频、抽帧数据、虚拟环境或模型权重进入 Git diff。

不要先花大量时间堆与真实工作流无关的测试。优先用一个真实 NAS 视频把“导入 → 抽帧 → 事件分组 → 人工标注 → 恢复 → 导出”完整走通，再补少量覆盖关键数据转换和切分规则的测试。

完成后向用户说明：

- 工具如何启动；
- 数据存在哪里；
- 第一次应该选择哪些视频；
- 如何标第一批 30～50 个独立结算事件；
- 哪些功能已经完成；
- 哪些内容明确留到模型训练阶段。
