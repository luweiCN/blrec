# 训练数据规范

## 数据原则

### 人工确认才是真值

Worker 和旧模型可以给出建议标签，但建议只用于排序和省去重复操作。只有人工确认的标签才能进入训练集；后续模型预标不能覆盖人工结果。

### 训练资产与临时候选必须分开

数据按生命周期分为四种状态，不能把“模型预标”或“已经冻结”笼统写成“已经参与训练”：

| 状态 | 含义 | 保留规则 |
|---|---|---|
| 临时候选 | Worker 上传但尚未人工确认 | 可以在后续制定保留期后清理 |
| 已确认、未冻结 | 人工已经确认，但还没有进入数据集快照 | 必须保留，直到进入快照或被人工明确作废 |
| 已冻结数据集 | 已生成不可变版本清单的 train／val／test 样本 | 永久保留清单及其引用的图片和标签；不能依赖临时候选或原视频 |
| 已参与训练 | 某个 `training_runs.dataset_version_id` 引用的数据集快照 | 永久保留对应图片、标签、切分、清单、训练配置和产物 |

验证集和测试集虽然不参与梯度更新，也是复现和验收模型不可缺少的永久资产，不能按“没有参与训练”清理。NAS 的 `vision-data/candidates` 是候选区；任何清理工具都必须先排除人工已确认数据和所有数据集清单引用的 SHA-256。当前不提供自动删除，避免在保护规则完成前误删。

### NAS 增量存储目录规范

视觉数据不得放入 BLREC 的 `config` 目录。生产 NAS 统一使用与 `config`、
`log`、`rec` 同级的一级目录：

```text
/volume1/docker/blrec-next/vision-data/
├── candidates/       Worker 上传、尚未成为正式训练资产的图片和预标
├── objects/          按 SHA-256 去重的人工确认图片，每张原图只保存一次
├── labels/           人工标签及其修订历史
├── datasets/         不可变数据集版本清单和 train／val／test 切分
├── training-runs/    训练配置、指标、日志及数据集版本引用
└── models/           模型包、校验值和部署记录
```

本轮 Worker 部署只实现 `candidates/`，不得顺带实现或改写其他目录。后续数据层
实现必须遵守以下规则：

1. 新图片按 SHA-256 增量写入 `objects/`；相同图片不能因重新训练而复制。
2. `dataset-vN` 只新增不可变清单和切分，引用既有对象；不能复制完整历史图片。
3. 标签修正创建修订记录，不覆盖或丢失旧的人工结论。
4. 训练时生成的 train／val／test 实体目录属于可重建缓存，可以使用硬链接；
   训练结束后允许删除。
5. 任何被人工确认、数据集清单或训练记录引用的对象都禁止清理。

当前 Vision Lab 的本地 `data/datasets/<version>/` 仍是自包含快照。在共享
`objects/`、引用保护和恢复校验实现之前，不得删除这些现有快照；后续迁移者应
先按 SHA-256 导入对象池并验证全部清单，再切换为增量存储。

### 独立场景比连续帧数量更重要

同一界面持续十秒产生的四十张相似图片，不等于四十个独立案例。数据统计应同时看：

- 代表帧数量；
- 独立事件或对局数量；
- 视频／录制场次数量；
- 主播和设备环境数量。

每个事件优先保留 3～6 张真正有差异的帧，例如淡入、完整显示、局部遮挡、窗口化和即将消失的状态。

### 模型看不清的图不要硬猜

人工也无法可靠判断的图片标为 `unreadable`、`unknown` 或“无证据”，并从对应训练目标排除。它不能被错误地塞进负样本，否则模型会学到矛盾规则。

### 训练与运行预处理必须相同

- 保持原始宽高比，使用 letterbox 补边，不把不同设备画面强行拉伸成正方形。
- 有可靠 `viewport_bbox` 时可以裁出游戏画面；没有时使用完整画面，不靠视频宽高比猜裁剪位置。
- 明确记录 RGB／BGR、缩放范围、归一化参数、补边颜色和输入尺寸。
- 任何裁剪都必须映射回原始分辨率坐标，OCR 始终使用原始画面区域。

新 Vision Lab 分类模型统一使用 512×288 的 16:9 画布：保留完整原图、等比缩放、不裁切、不拉伸，空余区域补边后再做 ImageNet 归一化。训练时随机改变中性补边颜色、额外边宽和内容位置，并且对所有类别使用同一规则，避免模型把某一种黑边或灰边当成类别特征；验证和推理固定使用 114 灰边，保证结果可复现。原始训练快照不改写，随机补边在每个 epoch 读取图片时生成，不会让数据集不断复制膨胀。

现有生产 `multi-v2` 仍使用旧的正方形输入。Analysis Worker 接入新模型包时必须逐项读取清单中的宽高、补边和归一化规则，不能复用旧 `multi-v2` 的拉伸逻辑。结算检测继续使用 640×640 letterbox；头像位置检测为了保留很小的 HUD 头像，第一版使用 960×960 letterbox。英雄身份分类只处理已经裁出的正方形头像，第一版输入为 160×160。主播本人位置分类保留完整积分板或结算图，使用 512×288 全图 letterbox，不能只裁圆形头像，因为本人高亮可能落在整行背景上。

## 历史专项标注规则

### 1. BP 模式分类

#### 正确标签

- 能明确看出是 3V3 英雄选择：`bp_3v3`。
- 能明确看出是大乱斗随机英雄选择：`bp_aram`。
- 能明确看出是 5V5 英雄选择／征召：`bp_5v5`。
- 画面不是 BP：`not_bp`。

接受／拒绝匹配必须标为 `match_confirm`，导出时映射到 `not_bp`，不能标成任一模式 BP。

#### 画面条件

| 条件 | 是否进入训练 | 规则 |
|---|---|---|
| `clear` | 是 | 默认情况 |
| `occluded` | 是 | 遮挡后仍能由人工可靠确定模式 |
| `windowed` | 是 | 小窗或非全屏，但模式仍可确认 |
| `occluded_windowed` | 是 | 同时遮挡和小窗，仍能确认时保留 |
| `unreadable` | 否 | 模式看不清，不得改标成 `not_bp` |

#### `not_bp` 要采什么

不要只采匹配确认。至少覆盖：

- 排队和匹配确认；
- 阵容确认、加载和天赋选择；
- 游戏内计分板、商店和普通战斗；
- 游戏外大厅和英雄列表；
- BP 前后的过渡帧；
- 外部遮挡恰好露出类似 BP 卡片的画面。

建议每种难负样本来自多个视频，防止模型只记住某一个主播的覆盖层。

### 2. 关键界面分类

#### 标签边界

- `result_page`：比赛已经结束，并显示最终胜负和整局数据的真正结算页面。
- `scoreboard`：比赛仍在进行时临时打开的玩家数据面板，包括死亡计分板。
- `other`：其他所有画面，特别要包含胜负动画、结算页关闭后的背景和加载转场。

是否出现 `REPLAY` 字样或 OCR 识别出某个词，都不能代替人工按画面语义判断。

有遮挡但仍看得出是哪类的图片可以保留；完全看不清的设为 `unreadable` 并排除。

### 3. 结算面板检测

- `result_page` 必须画 `result_panel` 框后才能作为正样本。
- 框紧贴完整结算面板，不能只框标题、某一队或文字区域。
- 没有框的 `result_page` 应被排除，绝不能作为负样本。
- 计分板、死亡计分板、胜负动画、普通游戏、商店、黑屏和窗口化桌面都可以作为负样本。
- OCR 清晰度、半透明和遮挡是辅助属性，不改变“是否真正结算页”的标签。

电脑端、手机端、全屏、小窗、黑边和主播覆盖层都要有代表样本。结算面板位置和大小应由模型框决定，不能按整段视频宽高比套固定裁剪。

### 4. 大乱斗光栅检测

#### `blocked_gate`

- 一张图可以有多个光栅框，每一处清楚可见的光栅单独框选。
- 一个框只包一处黄色阻挡光栅，尽量紧贴目标。
- 光栅被 UI 或人物部分挡住但仍能辨认时可以标；完全无法确认时跳过。

#### `open_entrance`

- 只有镜头清楚拍到同一地图入口，并能确认本应横向阻挡的位置没有光栅时才标。
- 在工作台中圈出对应入口位置，用于人工复核和数据追溯。
- 当前单类检测导出会把整张图作为无框难负样本；`open_entrance` 框不会变成第二个检测类别。

#### `no_evidence`

镜头没拍到入口、入口太模糊或无法判断时选择无证据并跳过。这类图不作为 3V3 负样本。

### 5. 画面状态分类

通用标注向七类目标映射如下：

| 目标标签 | Vision Lab 来源 |
|---|---|
| `not_vainglory` | `content_family = not_vainglory` |
| `out_of_match` | 虚荣画面且 `game_context = out_of_match` |
| `pre_match` | `game_context = pre_match` |
| `in_match` | `game_context = in_match`，但排除 `talent_select` |
| `talent_select` | `screen_type = talent_select` |
| `post_match` | `game_context = post_match` |
| `transition` | `game_context = transition` |

`unknown`、草稿、待复核和缺少必要层级的标注不进入训练。`in_match` 数量最多，导出时要按具体界面和事件限量，保证商店、计分板、暂停等覆盖层不会被普通战斗完全淹没。

## 必须覆盖的数据差异

每个模型都应尽量覆盖以下变化，而不是靠设备宽高比做规则：

- 手机、平板和电脑模拟器／电脑端画面；
- 全屏、小窗、黑边、不同 UI 缩放和非标准分辨率；
- 不同主播、直播覆盖层、聊天框、摄像头和通知遮挡；
- 高码率、低码率、模糊、偏色、过亮、过暗和压缩块；
- 3V3、大乱斗、5V5，以及真人、人机、观战和回放；
- 界面出现、稳定、关闭和淡出前后的不同阶段。

设备、主播或宽高比属于数据属性，不是模式标签。若模型在某个主播上表现特别好，应先检查是否记住了覆盖层或画面比例。

## 数据切分与防泄漏

1. 当前最低要求是按 `video_id` 整体切分，不能让同一视频进入多个集合。
2. 同一录制场次的多个分 P、同一事件的连续帧和感知哈希近似重复图，应放在同一集合。
3. 条件允许时再按主播分组检查跨主播泛化，但不要为了“跨主播”导致某个稀有类完全没有验证样本。
4. 固定一份人工复核的测试集，后续主动学习和补数据不得把它重新加入训练集。
5. 每个稀有类至少有多个独立视频后再做正式指标；只有两个视频时，训练页能运行不代表结果可部署。

### 固定基准与训练后滚动挑战集

每个 training run 的 `train`／`val`／`test` 快照保持不可变。后续人工确认的
新数据不能追加或覆盖到旧 run 的 `test` 目录，而是为该 run 动态形成
`post_run_challenge`：

1. 人工确认时间晚于该 run 完成时间；
2. 当前任务标签有效且图片仍可读取；
3. 样本键不在该 run 的 train／val／test manifest 中；
4. 模型建议、待确认和看不清数据不进入挑战集；
5. 以后重新训练时，如果该图片已经进入新 run 的任一 split，它不会再充当该
   新 run 的滚动挑战样本。

页面必须分开报告“冻结测试集”和“训练后新增挑战集”，不能把两个准确率合并成
一个数字。滚动挑战可以包含与旧快照相同视频中后来确认的新帧，因此报告还应显示
新增视频数量；只有来自 run 未见视频的子集才代表更强的跨视频泛化证据。

人工修正了旧快照中某张图片的标签时，工作库记录新的真值，但旧 run 的冻结报告
仍代表当时的数据事实。该图片不能用新标签再次测试同一个 run；界面应把它计入
“旧成员标签已修正”，提示下一版重新冻结和训练。

### 训练卡片的数据增量

每个任务卡片同时展示：

- 最近成功 run 及其实际冻结样本数；
- 当前符合训练条件的人工真值数；
- 相对该 run 的新增样本、移除样本和标签修正数；
- 新增样本的类别和独立视频分布。

结算检测还要区分“全部有效人工真值”和“按 1,500 个负样本上限实际会入选的
候选快照”。否则已有几千张负样本时，继续增加普通负样本会显示很大的数字，却
不一定改变下一次训练数据。

建议比例为约 8:1:1，但分组完整性和每个标签在验证／测试中存在，比精确比例更重要。

## 数据增强边界

可使用轻微亮度、对比度、压缩噪声、模糊、缩放和局部遮挡增强。以下增强默认禁用或需要单独验证：

- 垂直翻转；
- 会把文字和左右 UI 镜像的水平翻转；
- 让黄色光栅变成其他颜色的大幅色相变化；
- 会裁掉 BP 关键布局、光栅或结算面板的激进随机裁剪。

增强不能替代真实的电脑端、小窗、遮挡和低码率样本。

## Worker 辅助收集

Worker 内部仍会复用五种旧模型输出：

- `screen_state`：低频粗扫的各状态代表帧；
- `bp_review`：开局附近的 BP 模式候选；
- `key_screen_review`：结算页、计分板和其他关键界面；
- `result_detector`：检测命中及计分板／胜负动画难负样本，命中时附建议框；
- `mode_gate`：3V3／大乱斗普通战斗帧，作为对局模式预标参考。

Server 会按图片 SHA-256 合并这些输出，实际落盘为一个 `unified_review` 候选，
其中 `suggestions` 最多包含 `match_flow`、`match_mode`、`hero_select` 和
`result_panel` 四项。相同图片不会因多个旧模型命中而复制。结算命中会分别保留
高置信代表帧和低置信边界帧；BLREC 已识别对局的历史结算截图也作为待确认来源
导入。所有预标都留在来源表，人工确认前不会进入训练集。

候选不能只按“不确定度”挑选。每个任务必须分层保留：

- 最低置信度或类别分歧样本，用于修正模型短板；
- 少量高置信正样本，用于持续覆盖正常清晰画面；
- 少量高置信负样本和 hard negative，用于抑制误报；
- 新主播、新分辨率、新宽高比、遮挡和半透明画面，即使高置信也抽样审计。

同一局、同一标签和相似时间点先去重并限额。高置信预测仍需抽样人工确认，
因为“很自信地认错”比普通低置信错误更需要进入下一轮训练。

后续主动学习还可增加更精确的选择原因：

- 状态模型低置信度、前后状态冲突和切换边界；
- 结算检测命中但关键界面分类反对的分歧样本；
- 结束边界存在但整个窗口没有结算命中的疑似漏检；
- 模式证据冲突、光栅低置信度命中和相似黄色物体；
- OCR 失败但结算检测与关键界面分类均通过的清晰画面。

上述分层采集是新模型验收并接入 Worker 后的目标策略，不提前套用到当前旧
`multi-v2` Worker。现阶段旧 Worker 保持原有扫描和候选行为；旧模型新产出的
候选不要求人工补画英雄框，也不进入新模型训练快照。新模型先以影子模式验证，
确认精度、速度和预标结构后，再启用分层采集与原视频高清回源。

## 每轮训练的固定流程

1. 修正并确认新增标注。
2. 查看按标签、视频、主播、画面条件和事件统计的缺口。
3. 点击训练时冻结新的 `*-vN` 数据集快照。
4. 记录快照规则、样本清单、Git 提交、标签顺序和数据分布。
5. 训练生成新 run，不覆盖以前的 run。
6. 在固定测试集和完整录像上验证。
7. 只有通过验证的 run 才能组装成模型包；“设为本机测试模型”不等于生产发布。
