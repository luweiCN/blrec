# 虚荣对局分析：模型接入改造总结与规划（2026-08-08）

本文档记录 2026-08-08 当天完成的虚荣对局分析流水线改造：遇到的问题、采用的
技术方案、两个视觉模型（multi-v2 / result-detector-v1）的用法与已知问题，
以及后续改进规划。

## 一、今天遇到的问题

### 1. 漏局（最严重，反复出现）

| 案例 | 现象 | 根因 |
|---|---|---|
| 虚荣55 的 840 局（at 3591.25s） | 反复漏检 | 结算画面被分类模型误判为 gameplay（victory_defeat 识别率仅 13.6%），结算后 109 秒画面也被误判 → 两局桥接成巨型对局段，窗口只在段尾生成，段中间结算无窗口 |
| 虚荣•vaingloryyyyoii～～ 的 3259 | 漏 3 局（3692/5385/6422s） | 同上：结算被误判 gameplay → 对局段不断 → 段尾窗口覆盖不到段中间结算 |
| 虚荣复活了!大家快回来玩吧 的 3265 P2 | 漏 4251.5s 局 | 结算后 44 秒画面被判 gameplay，段尾窗口前推 40s 差 3.5s 没够着；且该主播结算界面仅 0.几秒、结算后直接连打下一局（无退出信号，回归不触发） |

**共性根因**：结算画面（含胜负动画）被分类模型误判为 gameplay → 对局段结束点
被高估 40s~数分钟 → 依赖"段尾 + 前推 N 秒"的窗口覆盖不到真实结算。前推距离
是经验赌注（40s / 180s 都不保险）。

### 2. 模式误判

| 问题 | 根因 |
|---|---|
| 3v3 局被判大乱斗（3259 的 782 局） | 模式判定过度依赖 mode 头，gameplay 帧的 mode 头在生产环境系统性误判（该主播画面 20 帧全判 aram） |
| 5v5 局被判 3v3（3253/3265/3281） | 三层防线全失效：选英雄界面 mode 头没学到 5v5（实测 pre_match 帧全判 3v3）；检测模型面板宽高比把 5v5 判成 3v3；NAS 落库时用 OCR 槽位 max(slot) 重算（半透明面板槽位解析乱） |

### 3. 性能问题

| 问题 | 根因 |
|---|---|
| 5s 采样粗扫 2h 视频要 11 分钟 | classify_frames 漏加 `skip_frame=nokey`，fps=1/5 过滤器被迫解码全片 21.6 万帧 |
| 单核解码 2.5x 实时 | ffmpeg 命令写死 `-threads 1`，10 核机器只用 1 核 |
| 分类模型每帧 56ms | multi-v2 44.7MB fp32，比检测模型（12.3MB）慢 3.7 倍 |

### 4. 工程问题

| 问题 | 说明 |
|---|---|
| 页面日志 30 秒重复 | 每次心跳都携带同一状态，服务端每条心跳追加一条事件日志 |
| 阶段累计秒数显示 0 | worker 心跳状态里 elapsed_seconds 写死 0，analyzer 内部真实耗时没接上心跳 |
| 任务卡住不恢复 | recover 只在 worker claim 时触发，worker 忙时不 reclaim 停滞任务 |
| 改数据库重置任务导致 complete 400 | 把正在 analyzing 的任务重置为 pending，complete 的状态机不匹配 |

## 二、改造与技术方案

### 1. 级联扫描架构（替代旧 dense 全片）

```
粗扫（分类 5s 流式）→ 窗口推断 → 窗口内 4 FPS 检测 → 候选 → OCR 验证
```

### 2. 锚点机制（对局开始信号）

- 选英雄界面（pre_match 连续段 ≥2 帧）→ 锚点
- 锚点后 5 分钟内出现 gameplay → 对局确认（5v5 长 BP 不误杀）
- 锚点后先出现新锚点 → 前一局报废（秒退/取消）
- 对局段在锚点处切分（巨段桥接根治）

### 3. 回归机制（结算定位兜底）

- 退出信号（游戏外/转场/非虚荣）→ 4 FPS 检测从退出点往前扫到该局锚点
- 段尾窗口无命中 → 自动回归：4 FPS 从锚点扫到段尾窗口起点（覆盖连打主播等
  无退出信号的场景）

### 4. 模式判定（只信明确界面）

- 大乱斗：天赋选择界面帧（stage=天赋选择 且 mode=大乱斗）≥2 帧
- 5v5：选英雄界面帧 mode 头投票（≥8 帧且主票 ≥50%）；积分板/结算页帧 mode 头 ≥2
- gameplay 帧的 mode 头完全排除（3v3/大乱斗同地图不可信）
- team_size==5 优先于 hint
- OCR 玩家数 ≥10 → 强制 5v5（面板宽高比不可靠的兜底）
- NAS 落库信任 worker 判定（仅 unknown 时用 team_size 兜底）

### 5. 性能改造

- `skip_frame=nokey` + 流式采样：粗扫 2h 视频 11 分钟 → 约 1.5 分钟
- 6 核解码（`-threads 6`）：2h 视频解码 114s（单线程 702s，快 6.2 倍）
- 测速结论：VideoToolbox 硬解在测试视频上卡死，多线程软解胜出

### 6. 特殊主播方案

- 名单机制：NAS claim 携带 anchorName → worker 比对名单 → dense 4 FPS 全片扫描
- 适用：直播画面叠加元素（摄像头/贴纸/弹幕）导致模型失效的主播
- 名单匹配计划改为 room_id（主播名会改）

### 7. 工程改造

- 日志：状态变化才发送（同状态心跳只带进度）
- debug 模式：保存可疑帧（talent/aram）和候选帧（candidate-XXXms.png）
- worker 并发（--concurrency）+ 阶段耗时打点（任务耗时明细日志）

## 三、两个模型的用法与存在的问题

### multi-v2（分类模型，44.7MB，输入 224×224）

**用法**：
- 粗扫：5s 采样全片，content/stage/mode 三头
- stage 8 类：gameplay/scoreboard/result_page/victory_defeat/pre_match/
  out_of_match/transition/talent_select
- 模式判定：只信界面帧（选英雄/积分板/结算页/天赋选择）的 mode 头

**存在的问题**：
1. **结算画面识别率低**：victory_defeat 仅 13.6%（几乎全误判 gameplay），
   result_page 60%——这是漏局的总根源
2. **mode 头在 gameplay 帧上不可信**：3v3/大乱斗同地图单帧不可分；部分主播
   画面被系统性误判（20 帧全判 aram、14-28 帧判 5v5）
3. **out_of_match 训练样本太少**（val 仅 20 张）：大厅/结算后画面形态覆盖不足，
   特定主播画面被误判 gameplay
4. **pre_match 未细分**：大乱斗 BP（hero_select_aram）没有独立类别，无法用
   选英雄界面直接判定大乱斗
5. **对叠加直播元素的主播完全失效**（特殊主播名单兜底）

### result-detector-v1（结算面板检测，12.3MB，输入 640×640）

**用法**：
- 窗口内 4 FPS 精扫，输出结算面板 bbox + 置信度（recall 1.0）
- bbox 构造 viewport（OCR 裁剪区域）
- 特殊主播 dense 模式全片 4 FPS

**存在的问题**：
1. **面板宽高比判 team_size 不可靠**：5v5 面板被判 3v3（导致 5v5 误判，
   已用 OCR 玩家数修正兜底）
2. **半透明/遮挡面板**：部分候选帧检测到面板但布局验证失败
   （rejected_layout），或 OCR 读不全（槽位/玩家数）
3. 生产场景（低分辨率帧、卡顿帧）的 recall 未经系统验证（val 1.0 是训练分布）

### 2. 中期（模型改进，1-2 周）

- [ ] **补训练数据重训 multi-v2**（收益最大）：
  - 结算画面 + 胜负动画（当前识别率 13.6% 的短板）
  - 游戏外/大厅各种形态（out_of_match 样本扩充）
  - 叠加直播元素的主播画面（特殊主播的样本）
  - 低分辨率帧（训练/推理分辨率对齐）

- [ ] mode 头训练改进：5v5 与 3v3/aram 的区分（选英雄界面差异明显，
      模型应能学到）
- [ ] multi-v2 量化（fp16/INT8）：粗扫提速 2-3 倍

### 3. 长期（架构演进）

- [ ] **候选验证分层**：对检测置信度高但布局验证失败的候选，放宽验证或
      直接尝试 OCR（遮挡场景）
- [ ] 窗口推断参数基于真实样本调优（锚点确认窗口、回归扫描成本的平衡）
- [ ] 特殊主播的"笨办法"进一步优化（dense 只扫可疑区域而非全片）
- [ ] 观察多主播样本后，评估是否把"锚点 + 回归"推广为唯一路径
      （去掉固定前推窗口）
